# dbtrope

A dbt project that composes music. Pieces are written in YAML, turned into a score with SQL, synthesized sample by sample in DuckDB, and written to WAV.

## Commands

- `make install`: create `.venv` and install dbt-duckdb
- `make registry`: regenerate `macros/registry.sql` from `models/pieces/*.yml` and `models/instruments/*.yml`; run after adding, renaming or removing a piece or instrument (`make parse`, `check` and `build` run it first)
- `make new-piece NAME=…`, `make new-instrument NAME=…`: create a piece or stored instrument from `templates/`
- `make check`: `dbt parse`, then check layer and naming rules (`scripts/check_layers.py`)
- `make build`: `make check`, then `dbt build`
- `make build TARGET=ci`: build against an in-memory DuckDB, as CI does
- `make docs`: generate and serve dbt docs, a browser for every piece, instrument and model with lineage
- `make score PIECE=…`: list a built piece's notes by bar and beat (`analyses/score_listing.sql`)
- `make clean`: remove `target/`, rendered WAV and MIDI files in `output/` and local `.duckdb` files

The dev database is `dbtrope.duckdb` in the project root; override with `DBTROPE_DUCKDB_PATH`. Rendered WAV and MIDI files go to `output/` (the `output_dir` var). The sample rate is the `sample_rate` var.

## Rules

- Write SQL following `docs/sql_style.md`. Read it before writing or editing a model.
- Layers are directories under `models/`: `pieces/`, `instruments/`, `base/`, `intermediate/`, `render/`. The table in `docs/sql_style.md` says what each may read.
- Only `intermediate/` models have a prefix: `int_{topic}__{transformation}`. Never use `stg_`. Other models are named for what they hold.
- Jinja only serialises piece and instrument YAML to JSON. Music logic belongs in SQL.
- Randomness must be deterministic: derive it from `hash()` of a seed and an index, never `random()`.
- Every model gets a YAML `description:` stating its grain. Models in `base/`, `intermediate/` and `render/` are documented in their directory's `_<directory>.yml` (`models/base/_base.yml`), in lineage order, with that directory's unit tests; never a per-model `.yml`. Pieces and instruments keep one `.yml` each. `make check` enforces this.
- Never edit `macros/registry.sql` by hand; it is generated by `scripts/build_registry.py`.
